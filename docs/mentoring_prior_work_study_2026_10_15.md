# 멘토링 후속 스터디: LLM 개인정보 보호·보안 프록시의 기존 시도와 한계

- 조사일: 2026-10-15 (Asia/Seoul)
- 목적: 기존 접근의 성과·남은 한계를 파악하고, 우리 MVP에서 검증할 좁은 문제를 정한다.
- 방법: 논문·프로젝트 원문을 확인한 문헌 조사. 아래 연구를 직접 실행하거나 성능을 재현한 결과가 아니다.
- 구분: **자료가 보고한 사실**, **우리 프로젝트에 대한 해석**, **아직 실행하지 않은 검증 제안**을 분리한다.

## 1. 멘토 피드백을 어떻게 이해해야 하나

질문은 “왜 아무도 만들지 못했는가?”보다 “이미 무엇이 가능하며 어떤 조건에서 한계가 나타났는가, 같은 한계를 우리도 갖고 있지 않은가?”로 정리하는 것이 적절하다.

이 조사에서 확인한 것은 특정 실험의 공격 우회, 오탐, 개인정보 보호와 답변 유용성의 상충이다. 이것으로 기존 기업이나 제품의 사업 실패, 현장 도입 실패, 기술 전체의 실패를 단정할 수 없다. 도입 비용·구매 의사·현장 운영 실패 원인은 고객 인터뷰와 별도 사례 자료가 필요하다.

## 2. 기존 접근 비교

| 접근 / 대표 자료 | 무엇을 해결하려 했나 | 자료에서 확인한 성과·한계 | 우리에게 남는 질문 |
|---|---|---|---|
| PII 탐지·비식별화 / Presidio | 민감정보를 찾아 마스킹·비식별화 | NLP·패턴·규칙·문맥을 조합한 도구가 이미 존재. 공식 README도 모든 민감정보 탐지를 보장하지 않음을 명시 | 단순 탐지 기능을 다시 만드는 대신 한국어 업무 데이터에서 어떤 오류를 줄이는가? |

| 방어별 적응형 공격 평가 / Zhan et al. | 방어를 아는 공격자에게도 견디는지 확인 | 평가한 여러 방어를 우회. 공격자의 내부 접근·첫 행동 중심·방어 단독 평가 등 조건이 있음 | 정해진 회귀 문장만 통과한 결과를 강건성으로 오해하지 않는가? |
| 더 강한 적응형 평가 / The Attacker Moves Second | 정적 공격·약한 최적화에 치우친 평가 개선 | 서로 다른 방어의 우회를 보고. 공격 지식·피드백·탐색 자원에 따라 해석해야 함 | 우리가 공개할 정보와 현실적인 공격 예산을 어떻게 정의할 것인가? |

각 행의 근거와 적용 범위는 다음 절에 정리한다. 이 표는 우리 구현과 동일 조건의 정량 비교가 아니다.

## 3. 자료별 읽을 내용

### A. Presidio: “마스킹 도구 자체가 없어서” 생긴 문제는 아니다

**자료 사실:** 공식 저장소는 PII 인식과 비식별화, 사용자 정의 recognizer를 제공한다. 인식 방법에는 NER, 정규식, 규칙, checksum과 문맥이 포함된다. 자동 탐지이므로 모든 민감정보를 찾는다는 보장은 없으며 추가 보호가 필요하다고 명시한다. 현재 Microsoft 경로는 새 프로젝트 저장소로 이동한다.

**해석:** 패턴과 모델을 결합한 PII 탐지는 이미 있는 접근이다. 우리 다층 탐지 구조만으로 최초·우수성을 주장할 수 없다. 문맥상 민감정보나 미탐지는 우리에게도 남는다.

**읽을 위치:** README의 Main features와 민감정보 완전 탐지를 보장하지 않는 경고. [Presidio 공식 저장소](https://github.com/data-privacy-stack/presidio)

### B. PAPILLON: 개인정보를 덜 보내는 것과 좋은 답변을 얻는 것은 다른 목표다

**자료 사실:** NAACL 2025 논문은 로컬 모델이 외부 모델에 위임할 질의를 만들고 결과를 조합하는 개인정보 보호 방식을 제안한다. 단순 삭제는 답변에 필요한 정보를 잃게 할 수 있다. 원문은 explicit PII 중심 평가, 단일 턴 범위, LLM 평가 의존, 과도한 삭제 및 원래 요청과 맞지 않는 추가 정보 생성 가능성을 한계로 설명한다. 연구가 개선을 보고했다는 사실과 완전한 보호·품질 보장이 아니라는 점을 함께 읽는다.

**해석:** 우리도 MASK 결과의 탐지율만 볼 것이 아니라 요약에 필요한 사실이 남는지 확인해야 한다. PAPILLON은 개인정보 보호·유용성 비교 대상이며 Prompt Injection 탐지기를 비교하는 기준으로 쓰지 않는다.

**읽을 위치:** Introduction, Task Definition, Conclusion, Limitations. [논문 원문](https://aclanthology.org/2025.naacl-long.173.pdf)

### C. PIGuard: 공격을 많이 잡는 필터도 업무를 방해할 수 있다

**자료 사실:** ACL 2025 논문은 공격에서 자주 등장하는 단어 때문에 정상 입력까지 악성으로 분류하는 overdefense를 다룬다. 정상 문장에 공격 관련 표현이 포함된 NotInject로 과잉 방어를 평가하고, trigger-word 편향을 줄이는 학습을 제안한다.

**해석:** “인젝션을 설명해줘” 같은 정상 문장도 막는다면 높은 차단율이 유용성을 의미하지 않는다. 우리 규칙·경량 분류기도 정상 업무 문장의 오탐을 별도로 평가해야 한다. PIGuard의 논문 성과를 우리 재현 성과로 사용하지 않는다.

**읽을 위치:** Abstract, NotInject 및 trigger-word bias 관련 분석. [논문 소개와 원문](https://aclanthology.org/2025.acl-long.1468/)

### D. Spotlighting: 외부에서 읽은 문장은 명령과 구분해야 한다

**자료 사실:** Microsoft Research의 2024 연구는 여러 출처의 텍스트를 한 입력으로 합칠 때 외부 자료의 지시가 사용자 명령처럼 처리되는 문제를 다룬다. 입력을 변환해 출처를 지속적으로 표시하는 방법을 제안하고, 해당 GPT 계열 실험에서 공격 감소와 업무 효용 보존을 보고한다.

**해석:** “악성 문구를 찾는 것”과 “누가 내린 지시인지 구분하는 것”은 다른 방어다. 이 연구를 실패 사례로 부르면 부정확하다. 다만 해당 실험을 모든 모델·새 공격·업무에 대한 보장으로 확대할 수 없다. 현재 우리 MVP에는 RAG·도구 실행 전반의 출처·권한 분리를 구현했다고 주장할 근거가 없다.

**읽을 위치:** 연구 소개의 문제 정의·출처 표시 방법·실험 범위. [공식 연구 소개](https://www.microsoft.com/en-us/research/publication/defending-against-indirect-prompt-injection-attacks-with-spotlighting/)

### E. Adaptive Attacks Break Defenses: 방어에 맞춰 공격을 바꾸면 결과가 달라진다

**자료 사실:** Zhan et al.의 2025 연구는 간접 인젝션 에이전트 방어들을 적응형 공격으로 평가해 우회를 보고했다. 원문 Limitations는 white-box 접근 가정, 첫 행동 중심 최적화, 방어 조합을 평가하지 않은 점을 명시한다.

**해석:** 알려진 고정 문장에 대한 성공만으로 강건성을 주장하면 안 된다. 동시에 이 논문으로 모든 배포 환경이나 모든 다층 조합이 무효라고 단정할 수도 없다. 우리에게 맞는 공격자 접근 범위와 시도 횟수를 명시해야 한다.

**읽을 위치:** Defense Techniques, Experiment Settings, Limitations. [원문 v2](https://arxiv.org/html/2503.00061v2)

### F. The Attacker Moves Second: 좋은 점수보다 평가 조건을 먼저 본다

**자료 사실:** 2025 연구의 v1은 정적 공격이나 방어를 고려하지 않은 약한 탐색으로 평가한 방어들을 더 강한 적응형 방법으로 시험한다. 원문은 공격자 접근을 내부 정보 접근, 출력 점수 접근, 최종 생성 결과만 접근하는 경우로 구분하고 상당한 탐색 자원을 가정한다. 여러 방어에 대한 우회를 보고한다.

**해석:** “보안 필터가 있다”와 “강한 공격에도 견딘다”는 별개다. 모델·방어 버전·공격 피드백·시도 예산·정상 업무 성공률을 함께 기록해야 한다. 평가한 특정 시스템의 결과를 우리 프록시 우회율이나 모든 최신 서비스에 적용할 수 없다. 이번 조사는 v1을 확인한 것이며 최신 버전 전체에 대한 검토를 주장하지 않는다.

**읽을 위치:** Abstract, Threat Model, Evaluation. [원문 v1](https://arxiv.org/html/2510.09023v1)

## 4. “왜 실패했나”를 설명하는 다섯 가지 축

1. **위험의 정의가 다르다.** 정형 PII 삭제, 문맥상 민감정보 보호, jailbreak 방어, 외부 문서의 지시 주입, 도구 권한 남용은 같은 문제가 아니다. 한 지표를 잘했다고 나머지가 해결되지는 않는다. 위 자료들의 대상 차이를 종합한 해석이다.
2. **보호와 유용성이 충돌한다.** 민감정보를 지우면서 답변에 필요한 사실도 지울 수 있다. PAPILLON이 직접 다룬 쟁점이며 우리 MASK 흐름도 같은 검증이 필요하다.
3. **공격 신호와 정상 표현이 겹친다.** 공격을 교육·인용·분석하는 정상 문장까지 막을 수 있다. PIGuard의 과잉 방어 문제와 연결된다.
4. **평가보다 공격자가 강해질 수 있다.** 고정된 입력만 시험하면 방어에 맞춘 변형을 놓칠 수 있다. 적응형 공격 논문들의 핵심 지적이다.
5. **운영 가능한 제품인지는 별도 문제다.** 지연·비용·세션·권한·키·원문 보존 정책·고객 업무 적합성은 모델 점수만으로 검증할 수 없다. 이는 우리 운영 제한 문서와 연결한 검토 항목이며, 특정 경쟁 제품이 이 이유로 실패했다는 관찰 결과가 아니다.

## 5. 우리 MVP의 위치: 해결했다고 말할 것과 아직 증명하지 못한 것

**현재 구현한 흐름:** 입력 탐지와 정책 집행, Provider 직전 마스킹·차단, 생성 후 출력 Validator, 일반 사용자·관리자 응답 구분, 원문을 남기지 않는 감사 메타데이터 기록이다. 구현했다는 것과 효과를 정량 입증했다는 것은 구분한다.

**그 자체로 차별성을 증명하지 못하는 요소:** 다층 탐지, 마스킹, 출력 검사, 관리 화면이 있다는 사실. 위 기존 접근과 같은 위험을 가진다.

**검증할 포지셔닝 가설:** 한국어 공공기관 업무 중 민원 요약 한 가지를 대상으로, 민감정보 노출 감소와 요약 유용성·허용 가능한 오탐·처리 지연을 함께 측정할 수 있는 정책 프록시. 아직 시장 우위나 기존 제품보다 나은 성능을 입증한 것은 아니다.

**추가 경계:** Validator는 생성 후 반환 전의 규칙 기반 검증 계층이다. SSE는 전체 버퍼링 후 검증하며 실시간 토큰 검증이 아니다. 감사 서명은 ML-DSA 교체 가능한 감사 로그 서명 인터페이스와 Mock signer 기반 검증 구조다. 실제 ML-DSA나 탐지 성능 향상 요소로 설명하지 않는다.

내부 회귀 성적과 외부 공개 데이터셋 성적은 [평가 한계](evaluation_limitations.md), [내부 평가](../reports/evaluation_report.md), [기존 외부 평가](../reports/external_prompt_injection_report.md)에서 분리해 읽는다. 외부 성능 한계가 남아 있는데 한국어 시나리오 특화라는 설계 의도만으로 우수성을 주장하면 안 된다. 실제 특화 이점도 별도 검증해야 한다.

기존 PAPILLON 구조 비교는 [기존 비교 문서](../reports/baselines/papillon_comparison.md)에 있으며, 이번 조사로 성능을 재현하거나 비교 수치를 갱신하지 않았다. Attention Tracker처럼 모델 내부 접근을 요구하는 방법은 [기존 관련 연구 문서](../reports/baselines/related_work_attention_tracker.md)에서 배포 조건 차이를 별도로 다룬다.

| 민감정보를 가려도 민원 요약에 유용한가? | 합성·비식별 시나리오에서 원문, 정형 마스킹, 정책 프록시 결과 | 외부 전송 전 잔존 PII, 요약의 필수 사실 보존, 사람이 평가한 유용성 | 개인정보 탐지와 답변 품질은 별도 지표. 실제 개인정보 외부 전송은 실험에 쓰지 않음 |
| 정상 업무를 불필요하게 막는가? | 정상 업무, 보안 교육·인용, 정책 우회 요청을 분리 | 입력별 FP/FN, 조치·사유, 판단 근거와 라벨 합의 | 규칙을 보정한 데이터와 최종 평가 데이터 분리 |
| 다층 구조가 실제로 추가 기여하는가? | Rule Only, Model Only, 결합 입력 검사, 출력 Validator 적용 전후를 구분 | 계층별 추가 탐지·추가 오탐·최종 유출, 지연 | 모델 artifact 상태·버전·해시 고정, fallback 별도 표시 |
| 방어에 맞춘 변형에도 동작하는가? | 정적 사례와 통제된 적응형 평가 | 모델·정책 버전, 공격자 지식·피드백·시도 예산, 성공 정의 | 문구 탐지 실패와 실제 정책 우회·유출을 구분. 로컬 통제 환경에서만 검증 |
| 운영 비용을 수용할 수 있는가? | 같은 장비·모델·입출력 길이·부하 조건 | 검사 자체와 전체 응답의 평균·p95, 오류·메모리·비용 | LLM 네트워크 시간과 프록시 오버헤드 분리. 50ms·동시 100건은 미검증 후보 |

먼저 고객 업무와 정답 기준을 고정하고, 동일 입력으로 기존 도구와 비교할 수 있는 최소 평가 계획을 만든다. PAPILLON·Presidio·인젝션 분류기를 목적이 다른데도 한 성능표로 순위를 매기지 않는다.

## 7. 다음 멘토링에서 설명할 결론

기존 시도는 이미 있으며 일부 효과를 보고했다. 남은 문제는 개인정보 보호와 답변 유용성의 상충, 정상 입력 오탐, 적응형 공격, 입력 출처·권한 경계, 평가와 운영 환경의 차이다. 우리도 이 한계를 자동으로 해결하지 못한다. 민원 요약처럼 좁은 업무에서 어떤 유용성과 보안 경계를 측정할지 먼저 정의하고 기존 방법과 같은 조건으로 검증하려 한다.

멘토에게 확인할 질문:

- 우리 비교 대상은 PII 비식별화 도구, privacy-preserving delegation, 인젝션 분류기 중 무엇을 우선해야 하는가?
- 민원 요약의 유용성과 잔존 민감정보를 어떤 정답 기준으로 평가해야 하는가?
- 적응형 공격의 현실적인 지식·피드백·시도 예산을 어떻게 정할 것인가?
- 신규 모델 제안이 아니라 업무별 정책 집행·평가 체계 구현으로 범위를 잡아도 적절한가?
