# 멘토링 조사: 기존 LLM 보안 제품, 평가 결과, 우리 MVP의 개선 방향

조사일: 2026-10-15. 제품 공식 문서·학술 원문·국책연구기관 보고서를 확인한 문헌 조사다. 제품을 구매하거나 논문 실험을 재현하지 않았다. 아래 수치는 전부 인용한 자료의 결과이며 우리 시스템의 성능이 아니다.

## 1. 결론부터

**비슷한 보안 제품도 있고, 효과 및 실패 조건을 측정한 연구도 있다. 기존 시도가 전부 실패했다는 근거는 없다. 우리 방향을 폐기할 이유는 없지만, 현재 기능 조합만으로 독창성이나 비교 우위를 주장하기는 어렵다.**

특히 국내 제품도 한국어 개인정보 마스킹, 다층 인젝션 방어, 감사 추적, 폐쇄망 배포를 함께 내세운다. 따라서 “한국어 공공기관 대상”, “입출력 검사”, “여러 기능의 통합” 자체를 검증된 차별점으로 쓰면 안 된다. 우리 개선 방향은 한국어 민원 업무에서의 탐지 누락·정상 요청 오탐·마스킹 후 정보 손실을 측정하고 줄이는 것으로 좁히는 것이 타당하다. 이는 조사 결과에 대한 제안이지 이미 달성한 성과가 아니다.

## 3. 실제 성과와 실패 조건이 측정된 연구

### A. Spotlighting: 효과가 있었지만 공격 조건을 바꾸자 한계가 드러남

- **초기 성과:** Microsoft Research의 2024 연구는 외부 문서의 출처를 표시하는 입력 변환으로, 해당 GPT 계열 실험에서 간접 인젝션 공격 성공률을 50% 초과에서 2% 미만으로 줄였다고 보고했다.
- **후속 결과:** The Attacker Moves Second의 2025 v1 부록 Table 7은 Spotlighting + MetaSecAlign 70B의 AgentDojo 평가에서 고정 공격 ASR 1%, 방어에 맞춘 탐색 공격 ASR 99%를 보고한다. 같은 표의 GPT-5 Mini 조건은 각각 0%, 47%다. 모든 모델에서 동일하게 실패했다는 뜻이 아니다.
- **왜 한계가 생기나:** 지시와 외부 자료를 구분하라고 모델에 요청하는 방법은, 공격자가 그 구분을 흔드는 새로운 문장을 탐색할 여지를 남긴다. 고정 공격에 좋은 점수만으로 강한 공격에 대한 방어력을 판단하기 어렵다.
- **적용 범위:** 두 연구는 모델·공격·평가 조건이 다르다. 초기 2%와 후속 99%를 동일 시스템의 운영 중 악화 추이로 비교하지 않는다. 후속 연구는 상당한 공격 자원과 방어별 접근 조건을 가정하며, 실제 공공기관 침해율이 아니다.

출처: [Microsoft 연구 소개](https://www.microsoft.com/en-us/research/publication/defending-against-indirect-prompt-injection-attacks-with-spotlighting/), [후속 연구 v1 §3, §5.1, Appendix G Table 7](https://arxiv.org/html/2510.09023v1).

같은 후속 연구의 Appendix G는 계획과 실행을 분리하는 CaMeL 등은 선택한 시나리오 다수에서 제어 흐름이 공격 데이터와 독립적이어서 공격이 성립하지 않는다며 이 비교에서 제외한다. 반면 적용 가능한 업무와 유용성의 제약을 지적한다. 따라서 “어떤 방어도 전부 무효”라는 결론은 내리지 않는다.

### B. 상용·공개 인젝션 탐지기: 문자 변형으로 탐지를 피함

- **평가 대상:** Hackett et al.의 2025 v1은 Azure Prompt Shield, Meta Prompt Guard, ProtectAI 등 탐지기를 평가했다.
- **수치:** 해당 논문 §5.1의 문자 변형 실험에서 Azure Prompt Shield의 프롬프트 인젝션 평균 탐지 회피율은 71.98%다.
- **수치의 뜻:** 이 논문 ASR의 정의는 공격 문장이 정상으로 오분류된 비율이다. 이를 개인정보 실제 유출률이나 최종 LLM의 정책 위반률로 바꿔 말하면 안 된다.
- **왜 한계가 생기나:** 문자 표기나 인코딩을 바꾸면 분류기는 공격 신호를 놓칠 수 있지만, 후단 LLM은 그 의미를 여전히 해석할 수 있다.
- **제한:** 476개 인젝션 입력과 논문 당시 버전·변형 방식의 결과다. 공격별 편차가 크며 현재 제품 전체의 성능을 대표하지 않는다. 다수 탐지기에 대한 내부 접근을 가정하지만 Azure는 black-box로 다룬다.

출처: [Bypassing Prompt Injection and Jailbreak Detection in LLM Guardrails v1, §4~5](https://arxiv.org/html/2504.11168v1).

### C. PAPILLON: 개인정보 노출 감소와 답변 품질 보존을 함께 평가

- **방식:** 로컬 LLM이 민감정보를 덜 포함한 질의를 만들고 외부 LLM에 위임한 뒤 답변을 조합한다.
- **결과:** NAACL 2025 Table 4의 Llama-3.1-8B-Instruct + GPT-4o-mini 조건에서, 프롬프트 최적화 전후 평균 품질 점수는 71.8→85.5, 평균 누출 점수는 17.4→7.50이다. 둘 다 0~100으로 환산한 논문 지표이며 PUPA-TNB 결과다.
- **해석:** 개인정보 보호와 유용성을 함께 개선한 실험 결과가 있다. 그러나 누출 점수가 0은 아니며, 개인정보 삭제가 답변에 필요한 정보까지 제거하는 문제가 남는다.
- **제한:** 명시적 PII·단일 턴 중심의 연구와 LLM 평가 지표다. 7.50을 공공기관 사고 발생 확률이나 공격 성공률로 해석하지 않는다. 한국어 민원 업무에서 같은 효과가 난다는 증거도 아니다.

출처: [PAPILLON 논문, §5~6 및 Table 4, Limitations](https://aclanthology.org/2025.naacl-long.173.pdf).

### D. PIGuard: 공격을 많이 막아도 정상 업무를 잘못 막을 수 있음

- **문제:** 공격에 자주 나오는 단어를 포함했다는 이유로 정상 문장을 악성으로 판정하는 과잉 방어.
- **평가:** ACL 2025 연구는 이런 정상 입력 339개로 NotInject를 구성했다. 일부 기존 모델의 정확도가 약 60% 수준으로 낮아지는 문제를 보고하고 개선 학습법을 제안했다.
- **우리 해석:** 보안 교육·공격 인용·정책 설명처럼 정상 업무에도 공격 단어가 등장한다. 우리도 이런 입력의 오탐을 측정해야 한다. 특정 벤치마크 성과가 모든 제품·언어에 적용되지는 않는다.

출처: [PIGuard 공식 학술 페이지 및 논문](https://aclanthology.org/2025.acl-long.1468/).

### E. CaMeL: 악성 문장 탐지 외에 실행 권한과 데이터 흐름을 제한하는 접근

2025 v2 논문은 신뢰한 사용자 질의에서 실행 계획을 만들고, 외부의 비신뢰 데이터가 실행 흐름을 바꾸지 못하도록 분리하며, 도구 호출 시 허용한 데이터 흐름만 통과시키는 방식을 제안한다. AgentDojo에서 논문이 정의한 보안 조건하에 업무 77%를 해결했다고 보고하며 무방어 시스템의 업무 해결률은 84%다. 이는 보안과 업무 수행률의 상충을 보여주는 해당 실험 결과다. 모든 시스템의 안전성을 증명한 것이 아니며, 현재 우리 MVP에 이런 도구 권한 통제가 구현되어 있다는 뜻도 아니다.

출처: [Defeating Prompt Injections by Design v2](https://arxiv.org/abs/2503.18813v2).

## 4. 국내 현장 조사도 있으나 공공기관 효과와 혼동하지 않음

한국보건사회연구원 「의료기관 사이버 보안 개선을 위한 정책 방안 연구」의 2025 조사 자료는 관련 질문 대상 57개 의료기관 중 LLM 특화 보안툴을 이미 도입한 곳 2개소, 시험 도입 중인 곳 3개소를 보고한다. 도입·시험 중 5개소에서 입력/출력 필터링을 선택한 곳은 3개소이며, 보안툴 만족도는 높은 편 2개소·보통 3개소다.

이는 국내 실제 도입·시험 및 만족도 조사 근거다. **이 기관들이 모두 공공기관이라는 근거는 확인하지 않았다.** 제품명·배치 방식·유출 감소량을 확인하는 비교 실험도 아니므로 공공기관 프록시 효과의 증거로 대체하지 않는다. 복수 응답 종류 표의 27.3%는 전체 선택 11건 대비 3건이므로 기관 비율로 오독하지 않는다.

출처: [한국보건사회연구원 원문](https://www.kihasa.re.kr/api/kihasa/file/download?seq=33038), PDF 438~440쪽, 인쇄 쪽수 423~425, 표 5-151~153.

국내 제도 자료로는 개인정보보호위원회가 2025-08-06 공개한 안내서가 유형별 위험 경감과 다층 안전조치를 다룬다. 이것은 특정 제품의 인증이나 우리 프록시의 공공기관 사용 승인이 아니다. [공식 공개 자료](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11410).

## 5. 우리 MVP에서 바꿔야 할 주장과 검증 우선순위

1. **주장 수정:** “이런 기술이 없었다/기존 방식이 전부 실패했다/통합만으로 우수하다”를 쓰지 않는다. “기존 기술의 한국어 민원 적용에서 남는 오류와 비용을 평가하는 프로토타입”으로 연구 범위를 제안한다.
2. **탐지 검증:** 같은 합성·비식별 한국어 민원 입력에서 기존 마스킹 도구와 우리 입력 검사를 비교한다. 주민번호 등 정형 PII와 문맥형 민감정보를 구분하고, 외부 전송 직전 잔존 정보와 정상 요청 오탐을 측정한다.
3. **마스킹 효용 검증:** 같은 LLM·질문·조건에서 요약의 핵심 사실 보존과 사람의 수정 시간을 함께 측정한다. 모든 입력 차단은 실무 성공으로 세지 않는다.
4. **계층별 추가 효과 검증:** 입력 검사, 생성 후 출력 검사 적용 전후를 나눠 추가 탐지·추가 오탐·지연을 기록한다. 같은 탐지기를 반복 적용한다고 독립 방어 두 개가 생기는 것은 아니다.
5. **변형 평가:** 정적 회귀 문장과 별개로 문자 변형·한국어/영어 혼합·문맥형 지시 우회를 로컬 통제 환경에서 평가한다. 탐지 회피와 실제 정책 위반을 다른 지표로 기록하고 공격 지식·피드백·시도 예산을 명시한다.

위 실험은 이번 조사에서 실행하지 않았다. 한국어 특화, 낮은 오탐, 빠른 처리, 기존 제품 대비 우위는 검증할 가설이다. 상용 제품을 직접 평가하지 않고 논문 표끼리 성능 순위를 만들지 않는다.

현재 구현 구분: PII 탐지와 인젝션 탐지는 별도 계층이며, Validator Agent는 생성 후 규칙 기반 출력 검증이다. SSE는 전체 버퍼링 후 검증으로 실시간 토큰 검증이 아니다. 감사 로그는 원문 prompt·response·API key·system prompt·개인정보를 저장하지 않는 원칙을 유지한다. 서명은 **ML-DSA 교체 가능한 감사 로그 서명 인터페이스와 Mock signer 기반 검증 구조**이며 실제 ML-DSA나 탐지 성능 개선으로 설명하지 않는다.

## 6. 멘토에게 답할 문장

> 국내에도 한국어 개인정보 마스킹과 인젝션 방어를 결합한 제품이 있습니다. 해외 연구에는 실제 효과와 우회 결과도 있습니다. 기존 시도가 모두 실패한 것은 아니고, 방어에 맞춘 공격, 정상 문장 오탐, 마스킹으로 인한 답변 품질 저하가 남아 있습니다. 저희도 같은 한계를 가질 수 있으므로, 기능 통합을 차별점으로 내세우기보다 한국어 민원 업무에서 기존 마스킹 도구 대비 누락·오탐·업무 품질을 검증하는 방향으로 좁히겠습니다.

## 7. 검증 기록

- 공식 제품 자료와 논문 원문, 국내 조사 보고서의 해당 표를 확인했다. 전수 조사 또는 현행 제품 재현 평가가 아니다.
- 코드·데이터셋·README 성능표·reports 수치를 변경하지 않았다. 기존 문서의 수치 불일치 문제를 이번 조사에서 수정하거나 기준으로 채택하지 않았다.
- 문서 변경 최소 검증: `git diff --check`, `git status --short --branch`, 문서 내 핵심 수치와 출처 URL 확인.
- 기존 `models/lightweight/classifier.joblib` 변경과 `.worktrees/`는 보존하며 커밋 대상에서 제외한다.
