# Ollama와 라우터의 기여도 후속 검증

- **기존 458건에서 추가 차단은 62건, 인젝션 추가 탐지는 4건이었다.** Ollama 응답을 `CLEAR/CLEAR`로 고정해 비교하니 추가 차단 중 2건은 라우터 규칙, 59건은 저장된 유효 판정, 1건은 타임아웃에 따른 차단으로 설명됐다.
- **합성·가상 민원에서 PII 잔존은 6/11건에서 1/11건으로 줄었다.** 보호된 5건은 `CLEAR/CLEAR` 대조군에서도 모두 차단됐다. 이 5건에서는 라우터 규칙만으로 보호 결과가 재현됐다.
- **11월 28일 Vulkan 실행에서 입력 경로 p95는 전체 458건 4.15초, Ollama를 호출한 70건 6.28초였다.** 11월 19일 CUDA 기록은 코호트별 p95를 제공한다.

## 라우터만 실행한 대조군

11월 28일 실제 Ollama 실행에서 저장한 판정과 상태를 동일 입력·분류기·라우터·정책으로 재생했다. 대조군은 라우팅된 요청에 유효한 `CLEAR/CLEAR` 판정을 주입했다. 기존 458건과 가상 민원 9건에서 라우팅 사유, 호출 대상, 실제 판정 재생의 탐지 및 차단 결과가 기록과 일치했다. 대조군의 로컬 API 호출은 0건이다. 재생은 새 모델 실행 없이 기존 판정이 정책 결과에 미친 영향을 검증한다.

| 평가 범위 | Hybrid | 라우터 + CLEAR | 라우터 + 저장된 실제 판정 |
|---|---:|---:|---:|
| 기존 458건 최종 차단 | 98 | 100 | 160 |
| 기존 4개 인젝션 코호트 TP 합계 | 104 | 104 | 108 |
| 합성 송신 PII 양성 5건 잔존 | 2 | 0 | 0 |
| 가상 민원 PII 양성 6건 잔존 | 4 | 1 | 1 |

기존 458건에서 라우팅된 70건 중 추가 차단은 62건이었다. 60건은 `CLEAR/CLEAR` 대비 추가 차단이며, 59건은 유효 판정, 1건은 타임아웃에서 나왔다. 내부 인젝션·deepset·Lakera에서 모델이 새로 표시한 PII 38건에는 PII 정답이 없어 검출 정확도는 미채점이다. 가상 민원에서는 실제 모델이 인젝션 오탐도 1건 추가했으나 해당 요청은 라우터가 이미 차단한 사례였다. 파인튜닝 후보는 라우터를 고정한 상태에서 추가 TP·FP와 마스킹 이후 잔존 방지 효과를 함께 평가할 필요가 있다.

## 내부 PII 추가 차단 21건

내부 PII 양성 40건에 기존 이메일·전화번호·주민등록번호·계좌번호 레이블의 위치를 부여했다. Adaptive에서 추가 차단된 21건에 대해 기존 Hybrid의 송신 준비 텍스트를 다시 채점했다.

| Hybrid 조치 → Adaptive 조치 | 추가 차단 | 기존 레이블의 전체 값이 남은 건 |
|---|---:|---:|
| MASK → BLOCK | 15 | 0/15 |
| WARN → BLOCK | 6 | 0/6 |

21건 모두 Hybrid 송신 준비 단계에서 정답 필드의 전체 값이 사라졌다. `WARN` 6건도 송신 가드에서 텍스트가 바뀌었다. 계좌번호 사례 한 건은 기존 레이블에 없던 예금주 이름을 별도로 채점하자 이름이 그대로 남았다. 따라서 21건에 대한 0/21은 기존 레이블의 전체 값 기준이다. 부분 마스킹에서 보존되는 문자와 문맥 재식별은 이 검사 범위 밖이다.

## 공공기관 업무형 정상 요청

`lakera_balanced_eval.jsonl`의 인젝션 음성 300건을 검토했다. 개별 문장 20건과 개인정보 값이 없는 업무 템플릿 조합 280건을 PII 음성으로 확인했다. Hybrid 및 Adaptive 차단은 각각 **0/300**이며, Adaptive 300건 모두 `clear_baseline`이었다. 이 결과는 고정된 업무형 코호트에서의 차단율이다. Ollama 판정에 노출된 정상 표본은 0건이므로 정상 요청이 모델로 라우팅될 때의 과잉 차단 비용은 남은 평가 과제다. ## 가상 민원 resident-01

회신 이메일 바로 뒤에 한글 조사가 붙어 이메일 정규식의 끝 단어 경계가 성립하지 않았다. 해당 위치에 공백만 추가한 대조에서 정규식 검출이 0건에서 1건으로 바뀌었다. 원래 입력에서 경량 분류기는 PII를 최상위로 골랐지만 점수 0.412는 검출 임계치 0.70과 라우팅 하한 0.60보다 낮았다. 나머지 라우팅 조건도 발동하지 않아 `clear_baseline`으로 처리됐고, 두 방식 모두 송신 준비 텍스트에 전체 값이 남았다. 이 유형은 이메일 경계 처리의 회귀 검증 대상으로 삼을 수 있다. ## 코호트별 입력 경로 p95

같은 표본의 Adaptive Hybrid 기준으로, 아래 값은 호출 여부와 관계없이 각 코호트의 전체 입력을 포함한다.

| 코호트 | 11월 19일 CUDA | 11월 28일 Vulkan |
|---|---:|---:|
| 내부 PII | 714 ms | 2,440 ms |
| 내부 인젝션 | 685 ms | 4,288 ms |
| deepset | 45 ms | 81 ms |
| ProtectAI | 31 ms | 57 ms |
| Lakera | 770 ms | 5,289 ms |
| 합성 송신 PII | 618 ms | 4,876 ms |

Vulkan 실행에서 호출 요청 70건만 모은 p95는 6,284 ms이며 타임아웃 1건을 포함한다. CUDA 쪽에 같은 70건 분모의 p95는 없다. 표의 코호트별 차이는 실행 환경의 영향을 보여 주지만, 런타임 버전과 시스템 부하도 달라 백엔드만 바꿨을 때의 차이는 별도 통제 실험이 필요하다. 측정 경로는 탐지·정책·송신 준비까지다. [11월 19일 결과](ollama_adaptive_results.md) · [CUDA 환경 기록](../docs/ollama_adaptive_detection.md#평가-실행-환경)
